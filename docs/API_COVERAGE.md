# Novu API coverage and compatibility

Reviewed against the official Novu API reference on September 5–6, 2026. “Documented” means contract research only; no Novu instance, credentials, n8n UI, or live request was used. The package exposes none of these operations in Batch 1.

## Compatibility baseline

- Authentication: `Authorization: ApiKey <secret>` ([authentication](https://docs.novu.co/api-reference/authentication)).
- Cloud hosts: `https://api.novu.co` (US) and `https://eu.api.novu.co` (EU). The credential stores a host/prefix without `/v1` or `/v2`; each operation owns its version ([API overview](https://docs.novu.co/api-reference)).
- Batch 2 validates custom bases as HTTPS origins with optional reverse-proxy prefixes, normalizes trailing slashes, and rejects credentials, query strings, fragments, malformed URLs, and final `/v1` or `/v2` path segments. All operation path segments are encoded. No TLS bypass or regional failover exists.
- The read-only credential test lists at most one v2 workflow. Its declarative response rules distinguish 401/403/404/429; n8n supplies standard handling for DNS, connection, and TLS failures. Execution transport maps those network failures and includes documented `Retry-After` context for 429 responses ([rate limiting](https://docs.novu.co/api-reference/rate-limiting)).
- Cloud documentation is the contract baseline. Self-hosted compatibility requires a pinned release and remains unverified ([self-hosting](https://docs.novu.co/community/self-hosting-novu/overview)).
- Pagination is endpoint-specific. Modern subscriber/topic/subscription lists use cursors; workflow listing uses `offset`/`limit` and returns `totalCount` ([pagination](https://docs.novu.co/api-reference/pagination)).
- The API reference presents an optional `idempotency-key` header broadly. API-layer idempotency is not enabled for every organization and the current documentation directs customers to contact Novu support to enable it. Where available, Novu retains records for a finite period and rejects a reused key with a different payload. Writes will expose or retry the header only where availability and semantics are verified. A caller-supplied `transactionId` remains a separate correlation/cancellation identifier and is not equivalent to atomic deduplication at the API boundary ([idempotency](https://docs.novu.co/api-reference/idempotency)).

## Deliberate scope adjustments and unresolved evidence

- The proposed Topic Subscription “Delete” is a bulk-style endpoint, not deletion at a guessed subscription-ID URL. Batch 7 must expose relationship selectors and partial results honestly.
- Workflow discovery uses current v2 workflow endpoints. The trigger still uses the v1 event endpoint and REST field `name`; SDK naming must not be copied into the REST body.
- Preference Get returns global and workflow settings together. Update chooses global or workflow scope through optional `workflowId`; schedule/context capabilities shown in the current schema are outside the first-release preference UI until a concrete use case is accepted.
- Cancellation remains in scope but only by transaction ID and only for active/pending execution. Recall of delivered messages is impossible by this operation.
- Omitted-field behavior, nullable clearing, subscriber custom-data merge/replacement, mutation empty-body shapes, permission differences, retry safety, rate-limit headers, and exact self-hosted parity require deterministic fixtures and/or live evidence in later batches.
- Outbound webhooks, agents/ACI, bulk endpoints, broadcast-to-all, workflow-definition editing, provider/channel administration, Inbox state, raw requests, and automatic legacy fallback remain deferred.
